### ✅ Canonical scheme (approved)

`PlayerStorageKeys` block, `40000`–`49999` (10,000 IDs, contiguous, sized per system by expected key count — not a flat 100 each). Systems expected to enumerate per-monster or per-node (talents, tasks, kill counters) got the largest blocks; flag-only systems stay small. There is enormous free space below this too (`31000`–`299999` is entirely open), so nothing here was sized under pressure — widen further later if a block actually fills up.

| Range | Size | System | Why this size |

**Explicitly requested as a permanent change despite conflicting with design rules 1 (preserve 8.6 feel) and 3 (protect PvP/economy) — flagged and confirmed before building.** Not a balanced-content feature; a deliberate, acknowledged departure from those rules for this server.

**Engine floor caveat — "10x" isn't uniformly achieved**: `MINSPAWN_INTERVAL = 10 * 1000` ("10 seconds, to match RME") is a hardcoded floor in `Spawns::loadFromXml` — any computed interval below it is silently clamped to 10s (not rejected, contrary to what I initially thought before checking — values are clamped, not dropped). The dominant original value, `spawntime="60"` (26,364 of the 32,395 entries — the vast majority of the map), can only reach the 10s floor: a **6x** speedup, not 10x. Only spawns with an original interval ≥100s got the full 10x. Full before/after distribution is in the commit; nothing was silently different from what's stated here.

**Regression found and fixed along the way**: rebuilding surfaced `[Warning - Monsters::loadMonster] Unknown loot item "silver dagger"` for `data/monster/monsters/zugurosh.xml` — a latent bug from the earlier Assassin dagger rename (item 2402: "silver dagger" → "assassin's dagger"). Zugurosh's loot entry referenced the item by `name="silver dagger"` only (no `id`), so the rename silently broke that loot drop from the very first Assassin restart onward. Fixed by updating the name to `"assassin's dagger"`. Three other bosses (`latrivan`, `witch`, `orshabaal`) also reference item 2402 but include `id="2402"` alongside the name — confirmed the loader trusts `id` when present and never actually validates the `name` string against it, so those were never broken; only name-only references break on a rename. Worth checking for this pattern (`grep -rln 'name="<old-name>"' data/monster/monsters/`, not just the numeric id) on any future item rename.

**PvP/economy impact (as flagged before building)**: the three changes compound — instant respawn with no player-visibility block plus 1000x EXP means a single character parked on any spawn point gets an unlimited, uninterrupted stream of monsters for near-infinite EXP/gold/loot. This removes any meaningful leveling curve and all spawn contention between players. No sink exists or could reasonably absorb this faucet. Confirmed as an intentional, permanent, explicit exception to design rules 1 and 3 — not an oversight.

### Universal base speed 415, uncapped per-level growth

**Explicitly requested — another permanent departure from 8.6 pacing, in the same spirit as the extreme-rates change above.**

| File | Change | Mechanism |
|---|---|---|
| `data/XML/vocations.xml` | `basespeed` raised from `220` (all 10 base/promoted vocations) and `230` (Assassin/Nightblade) to a uniform `415` across all 11 entries | **Container restart** — no hot-reload path for vocations |

**Finding — no engine change needed**: per-level speed growth already exists natively in this fork, undocumented until now: `src/player.h:1147`, `baseSpeed = vocation->getBaseSpeed() + (2 * (level - 1))`. Every vocation already gains **+2 speed per level** above 1; this is not vanilla Tibia behavior but is already built into this codebase, uncapped except by the engine's own `PLAYER_MAX_SPEED = 1500` ceiling (`src/player.h:81`) and `PLAYER_MIN_SPEED = 10` floor. So this change was purely a `vocations.xml` data edit — level 1 speed is now 415, level 50 is `415 + 98 = 513`, level 100 is `613`, climbing indefinitely toward 1500.

**Compounds with the extreme-rates change**: since EXP is already 1000x (see above), characters reach whatever level they stop at almost immediately — meaning the speed-per-level growth also kicks in almost immediately, not gradually. Same category of intentional departure as the rates change, not a new consideration, but worth having in one place since they interact.

### Auto-loot

**Deliberate QoL bend of 8.6-purity — explicit, conscious design choice, not a drift.** When a monster dies, its generated loot auto-moves from the corpse into the killer's equipped backpack, toggleable per player, default on. Economy-neutral: same loot table, same drop rates, same quantities — only delivery changes.

| File | Change | Mechanism |
|---|---|---|
| `data/scripts/eventcallbacks/monster/default_onDropLoot.lua` | Edited (this is the established extension point for loot generation, already handling stamina suppression/corpse ownership/party-loot messages before this change) — after the existing loot-creation loop, if the corpse owner has auto-loot enabled, attempts `item:moveTo(backpack, 0)` for each created item into their equipped backpack (`CONST_SLOT_BACKPACK`) | `/reload scripts` |
| `data/scripts/talkactions/autoloot.lua` | New — `!autoloot` / `!autoloot on` / `!autoloot off`, storage-backed, default on | `/reload scripts` |
| `data/lib/core/storages.lua` | Added `autoLootEnabled = 45900` — first key in the newly-carved **Player preferences/UI toggles** block (`45900`–`45999`, see storage table above) | **Container restart** — boot-only `dofile` chain, no reload path |

**Ownership — by construction, not by an added check**: `onDropLoot` only ever resolves to the corpse's already-established owner (`corpse:getCorpseOwner()`, set in `src/monster.cpp:1833-1849` to the individual player who dealt the most damage — same id `Player::canOpenCorpse` already uses for manual looting). Auto-loot only acts on this one player; it cannot hand loot to a non-owner, and doesn't touch any other player's ability to manually open the corpse. v1 scope: only the resolved owner gets auto-loot, not their whole party — other party members still loot manually as before (unchanged from pre-auto-loot behavior). Party-wide auto-loot is a possible v2, not built.

**Overflow safety — verified, not assumed**: `Item:moveTo()`'s default flags include `FLAG_NOLIMIT` (`src/cylinder.h:17`, "bypass limits like capacity/container limits") — calling it with defaults would force items into the backpack regardless of free space, silently defeating overflow safety. Fixed by passing `flags = 0` explicitly on every `moveTo` call, routing through the same capacity/slot-count validation a manual drag-and-drop uses. A full backpack makes the move fail and the item stays exactly where `createLootItem` put it — inside the corpse, fully visible and lootable by hand. Nothing is ever destroyed or duplicated: items are only ever created once by the untouched loot-generation loop; auto-loot strictly relocates them.

**UX fix applied during build**: the loot-broadcast message (`"Loot of X: ..."`) is now built from `corpse:getContentDescription()` *before* the auto-loot move happens, not after — otherwise a fully-auto-looted corpse would show an empty/misleading loot message even though items did drop, just not into the corpse.

**Gold**: no special-casing — gold coins are ordinary stackable loot items and flow through the same move-to-backpack path as everything else, stacking onto existing coin stacks normally. Confirmed goes to the bag, not `bankBalance`.

**Post-deploy fix**: the first build was completely broken — every kill threw `attempt to index a boolean value` at the `moveTo` line, meaning auto-loot silently did nothing (and worse, the loot-broadcast message likely never sent either, since the error aborted the function). Root cause: `Container:createLootItem()` is **not** a C++ binding — it's a pure-Lua helper in `data/lib/core/container.lua`, and it returns a **boolean success flag**, not the created `Item`. I misread the original script's `if not item then` check (which tests that boolean) as "the created item or nil on failure," and built a `createdItems` table full of `true`/`false` values, then tried to call `:moveTo()` on them. Fixed by dropping that assumption entirely: after the loot-generation loop runs (unchanged), the script now reads the corpse's actual contents via `corpse:getItems(false)` (non-recursive — top-level items/bags only, same scope as a manual drag) and moves those. This doesn't depend on any function's return value being an item reference, so it can't have the same class of bug. **Worth remembering: a Lua-callable method existing (`obj:method()` working syntactically) doesn't mean it's a C++ binding — some, like this one, are pure-Lua helpers layered into the metatable from `data/lib/core/*.lua`, and their return conventions have to be checked directly, not assumed from naming.**

**v1 scope note (per design)**: no item filter/whitelist — auto-loot moves everything the loot table generates. A future version could add a per-item or per-monster allowlist; not built here. (Superseded by the blacklist below, which adds an opt-out filter — the "no filter" note above describes the state at initial ship.)

**No level-up hook needed**: available points are derived live as `min(level - 1, 999) - spentPoints` on every read, never stored separately -- so a level-up needs no code to run at all (the next `!talent` call, or the next spend, just sees the new total). This also gives retroactive backfill for existing characters for free, no migration script needed.

**Engine mechanism, and a real pitfall found while implementing**: all 9 nodes' effects run through native `ConditionAttributes` params (`CONDITION_PARAM_SKILL_MELEEPERCENT`/`DISTANCEPERCENT`, `STAT_MAGICPOINTSPERCENT`/`MAXHITPOINTSPERCENT`/`MAXMANAPOINTSPERCENT`, `SPECIALSKILL_CRITICALHITCHANCE`/`AMOUNT`, `SPECIALSKILL_LIFELEECHCHANCE`/`AMOUNT`/`MANALEECHCHANCE`/`AMOUNT`) -- confirmed via `src/enums.h`/`src/combat.cpp`/`src/condition.cpp` before implementing, all natively supported, no C++ change needed. Confirmed `src/combat.cpp:795` (`Combat::doTargetCombat`) applies crit and both leech types to *any* player-caster damage, spells included, not just weapon hits -- every branch is genuinely useful to every vocation. Two encoding details that had to be gotten right: (1) the `*PERCENT`/`STAT_*` family is engine-encoded as `100 + extra%` (0 bonus = value `100`), while the `SPECIALSKILL_*` family is a raw value with no offset -- mixing these up would have made e.g. Fortitude either a no-op or a 100x HP multiplier; (2) unlike the existing `HEALTHGAINPERCENT`/`MANAGAINPERCENT` regen params (read fresh every tick, no snapshot), `ConditionAttributes::startCondition`/`endCondition` snapshot stat/skill/special-skill deltas **once** and apply/revert them as flat additions -- calling `condition:setParameter(...)` on an already-attached condition (the pattern `updateRegenPercent()` uses) does *not* recompute anything for these params. `Talents.applyBonuses` therefore always fully `removeCondition` then builds and `addCondition`s a fresh one from scratch on every change, rather than mutating a live condition in place.

**Reset**: free, gated to once per 24 in-game hours via `talentLastReset` vs `os.time()` -- prevents mid-fight PvP build-swapping without adding a gold sink, per the user's explicit choice when this was proposed.

**PvP/economy flag (per design rule 3)**: large, permanent, universal power increase -- every vocation gets equal access so no single vocation is favored, but this raises the overall PvP damage/sustain ceiling server-wide and compounds with the existing weapon-upgrade system's +32% attack at +13 (see that entry above). Total tree cost (~2,015 points across all 9 nodes) intentionally exceeds the 999-point budget at level 1000, so no character can ever max the whole tree -- that gap is the main brake on power growth, not a hard stat cap. Not yet balance-tested in practice; revisit if endgame PvP damage output turns out to move too far past what the existing systems already established.

### Loot Bag (designated auto-loot destination container)

**Post-deploy fix — id `12400` was the wrong pick, found by an actual boot failure**: first picked `12400` ("protective charm") for the rune of protection after the same repo-wide grep used for the other two reused ids came back clean. That grep only matched loot entries with an explicit `id="12400"` attribute — it missed `data/monster/monsters/amazon.xml:45` and `valkyrie.xml:51`, which reference the item **by name** (`<item name="protective charm" chance="..." />`, no `id` attribute at all, resolved by `Monsters::loadMonster` at load time). Restarting the container to test surfaced it immediately: `[Warning - Monsters::loadMonster] Unknown loot item "protective charm"` followed by `Cant load loot` for both monsters — renaming the item broke **their entire loot table**, not just that one line. Reverted `12400` back to "protective charm" untouched, re-checked candidates for both id- and name-based references this time, and moved to `12636` ("lizard essence," confirmed clean either way). **Lesson for the next reuse**: grep for the item's exact name string too, not just its numeric id — this repo's loot tables freely mix `<item id="X" name="Y">` and bare `<item name="Y">` forms, and only the id-based form shows up in an id-only grep.

**Post-deploy fix — real cause of "I can't use the runes at all", found by direct testing against the live server (not guessed)**: user reported using a rune produced a "must be used [with/on] an item" cancel message with no way past it — not a one-off, every attempt. Root cause: `10156`/`10531`/`12636` (the three originally-picked ids) all had **OTB `FLAG_USEABLE` unset** — a binary flag from `items.otb`, completely separate from anything `items.xml` can set (`src/items.cpp:550`, `iType.useable = hasBitSet(FLAG_USEABLE, flags)`, only ever assigned during OTB parsing). `src/game.cpp` gates both use paths on this flag before the action system is ever consulted: `playerUseItemEx` (drag one item onto another / "use with", `game.cpp:2097`) requires `isUseable() == true` and rejects with `RETURNVALUE_CANNOTUSETHISOBJECT` otherwise; `playerUseItem` (plain double-click, `game.cpp:2194`) requires the opposite (`isUseable() == false`) and calls the action with `target = nullptr` when it does fire. So every one of these three items could only ever be *plain*-used (never used-with-a-weapon), which is exactly why `weapon_upgrade.lua`'s own `target` validation kept firing — engine-level, not a bug in that script. Confirmed empirically rather than assumed: added a temporary `print()` scan (a startup globalevent, since nothing else could run arbitrary Lua without a live client this session) checking `ItemType(id):isUseable()` across item ids `8000`–`13000`; `data/scripts/actions/others/rust_remover.lua`'s and `saw.lua`'s own item ids (`9930`, `2558`, both confirmed working "use item on item" actions already in this codebase) came back `useable=true`, confirming the flag really is the gate, and even `2260` ("blank rune," an intermediate crafting material) came back `false` while `2313` ("explosion rune," an actually-castable spell rune) came back `true` — consistent with the flag tracking "genuinely meant to be used on a target," not just "is a rune." Widened the scan to require `isStackable()` too (the first replacement candidates picked, `9743`/`10614`, turned out `useable=true` but **not** stackable — unusable for a "buy/carry many" consumable), found `7759`/`8310`/`8301`, re-verified each for zero id- **and** name-based references (see the lesson above), and moved the three items there instead of the original picks. **This is now the standing checklist for reusing any existing item id in this repo**: (1) zero id references, (2) zero name references, (3) if the item needs to be used-with-a-target, `ItemType(id):isUseable()` must already be `true` in the shipped `items.otb` — items.xml cannot grant it, (4) if it needs to stack, `isStackable()` must already be `true` for the same reason.

**Why no new storage key**: level (and protection charges) live entirely on the weapon item instance via `ItemAttribute`/custom attribute, not on the player — exactly the case the pre-reserved **Item upgrades** storage block (`44000`–`44499`, see scheme above) already anticipated and explicitly deferred ("per-item upgrade state belongs on the item itself, not here"). That block stays unused by this feature; it remains reserved for any future player-level progression on top of this (e.g. an unlocked-upgrade-path flag), not for the level itself.

**Success rates** (both tiers consume the rune on success or failure):
- Tier I (safe — failure just wastes the rune): +1 100%, +2 95%, +3 90%, +4 80%, +5 70%, +6 60%, +7 50%, +8 40%, +9 30%, +10 20%.
- Tier II (risky — failure **downgrades the weapon by 1 level**, floor of +10, unless protected): +11 30%, +12 20%, +13 10%.

**Stat effect**: attack bonus recomputed from the weapon's base attack each time, not compounded — +2% per level for +1 to +10, +4% per level for +11 to +13. Max at +13: **+32% attack**. Applied via `item:setAttribute("attack", n)`, which persists correctly (`src/item.cpp`'s `serializeAttr`/`unserializeAttr` both handle `ATTR_ATTACK`).

**Wand/rod excluded from v1 scope (found and fixed during test-chest prep, not part of the original approved design)**: the original implementation included `WEAPON_WAND` and used `item:setBoostPercent(combatType, percent)` for a while during this round, since it scales cleanly across weapon types. Reverted both changes after finding two problems:
1. **`setBoostPercent` doesn't persist.** `src/item.cpp`'s `serializeAttr` (the save path) never writes `ATTR_BOOST` back out — only `unserializeAttr` (the read path) handles it, as legacy-format support. A boosted item would work for the rest of that session but silently lose the bonus on the next server restart, or possibly even a relog. Fails this feature's core premise outright, so not used for any weapon type.
2. **Melee/distance don't have this problem, but wands/rods have a different one.** Melee weapons' real damage is items.xml's `attack` attribute, read directly by the melee formula — `item:setAttribute("attack", n)` (persisted, confirmed above) scales it correctly. Distance weapons (bow/crossbow) have `attack="0"` in items.xml by design (real damage comes from the ammo) — `src/weapons.cpp`'s `WeaponDistance::getWeaponDamage` explicitly adds the equipped launcher's own `item->getAttack()` on top of the ammo's attack for any `WEAPON_AMMO` shot, so a **synthetic non-zero virtual base** (`distanceVirtualBaseAttack = 10` in the script) makes the same `setAttribute("attack", n)` approach work correctly for bows/crossbows too. Wands/rods have no such bolt-on: `src/weapons.cpp`'s `WeaponWand::getWeaponDamage` reads `item->getAttack()` too, but a **non-zero value there switches the whole formula** from the curated `min`/`max` in `data/weapons/weapons.xml` to a completely different magic-level-scaled formula (`Weapons::getMaxWeaponDamage`) — not a scale of the original curve, a substitution. Calibrating that safely needs its own design pass (e.g. a temporary magic-level buff condition applied via `data/movements/movements.xml` on equip, reapplied on login since equip events don't refire for items already worn at login), not a quick fix bolted onto this round.

**Net effect**: v1 covers Knight/Paladin/Assassin weapons (sword, club, axe, distance) correctly and persistently. Sorcerer/Druid wand/rod upgrading is **not implemented** — flagged here rather than shipped half-working; needs a follow-up design + approval per design rule 4 before it's added.

**Rune of protection (added this round)**: usable on a weapon at +10/+11/+12, stacks up to 5 `protectionCharges` (a custom attribute, tracked separately from `upgradeLevel`). When a Tier II attempt fails, a charge is consumed instead of the weapon downgrading — the physical rune is consumed immediately on use (like every other consumable here), but its *effect* persists on the weapon until an actual failure spends it, so an unused charge just sits there protecting the next attempt. This doesn't grant extra Tier II attempts (still gated by the rare rune of ascension drop) — it only removes the downside risk from attempts a player can already make, for a flat gold price.

**PvP/economy flag (per design rule 3)**: this is the largest deliberate permanent power gap shipped so far — a +13 weapon is +32% attack over an unupgraded one of the same type, bigger than the Assassin's vocation-level tradeoff. Mitigated by: the bonus being capped at 32% (roughly one weapon tier, not a snowball); Tier II material being drop-only and rare so +11–13 stays a minority long-term goal, keeping most PvP encounters at Tier I spread; and downgrade-on-fail making the push past +10 a genuine gamble rather than a guaranteed grind (protection runes soften this but don't remove the gold cost, and don't shortcut the rare-drop gate on attempts themselves). Gold sinks: Tier I's flat 5000g price combined with its own decreasing success chance (expected total gold cost to reach +10 rises steeply on its own, no price schedule needed); the protection rune's flat 15000g price. Tier II's sink is scarcity (rare drop) rather than gold.

**Scope note**: v1 covers melee weapons (sword/club/axe) and distance weapons (bow/crossbow). Wands/rods are excluded (see above). Ammo, shields, and armor are explicitly out of scope.

**Interaction bug — fixed, not just flagged**: this system and `weapon_upgrade.lua` originally each independently overwrote an item's `name`/`attack`/`description` by recomputing from `ItemType`'s static base plus only their own bonus — applying one after the other meant the later one won and the earlier system's bonus was silently erased (reported in live testing: upgrading a rare dagger to +1 made it display and behave as a plain, non-rare item). Fixed by centralizing all of it into one function, `Rarity.refreshCombinedDisplay(item, options)` in `rarity.lua`, called from both systems instead of each writing its own partial state:

| File | Change |
|---|---|
| `data/scripts/lib/rarity.lua` | `applyFlatBonus`/`clearFlatBonus`/`refreshDisplay` (three separate local functions) replaced by one `Rarity.refreshCombinedDisplay(item, options)` — reads BOTH `rarityTier` and `upgradeLevel` custom attributes off the item, sums their percentages, and recomputes attack/defense/armor/name/description from the item's true static `ItemType` base every time, regardless of which system triggered the refresh. `options.baseAttack` lets a caller override the true static base (needed for `weapon_upgrade.lua`'s distance-weapon virtual-base workaround); `options.extraDescription` appends caller-specific text (protection-charge count) this file has no knowledge of. `setTier()` (the shared helper behind `tryApplyOnDrop`/`reroll`/`forceApplyTier`) now only touches the rarity-specific custom attributes/action id, then defers to this function |
| `data/scripts/actions/others/weapon_upgrade.lua` | `getBonusPercent` promoted from a local function to a global `WeaponUpgrade.getBonusPercent`, so `rarity.lua` can read the same formula. `refreshDescription`/`applyLevel` rewritten to call `Rarity.refreshCombinedDisplay` instead of setting `attack`/`name`/`description` directly; all 3 call sites in `onUse` (rune success, rune downgrade-on-fail, protection-rune) updated to the new signatures | `/reload scripts` |

Net effect: a rare dagger upgraded to +1 now displays as "+1 rare dagger", with attack computed from the true base plus BOTH the rarity % and the upgrade %, combined additively on the same static base (not compounded on each other) — order-independent and idempotent no matter how many times either system re-triggers.
